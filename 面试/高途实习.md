## 干活内容

### 业务开发

#### 转介绍业务接口开发

- 背景：公司需要对用户沟通数据进行分析，判断一段数据中是否提及到“转介绍”以及客户的反应结果，据此做出后续推流

1. 沟通记录列表看板：listChatData，提取分析数据和对应ai的分析结果
2. 沟通记录详情：queryCommunicateDetail，提取分析数据详情，对应的ai结果和人工标注的结果，当中涉及到每一条沟通记录的开始时间和结束时间，需要通过调用asr（语音转文字）的api查询，解析其中的json字段对应加到结果中
3. 更新质检约束：抽取一条数据的ai分析和人工标注结果并进行对比，看两者是否一致，如果ai分析错误则需要更新结果

#### 用户反馈分析功能开发

- 背景：公司其他部门需要分析大批量的用户针对课程的反馈数据，以此来统计绩效，大概每个月需要分析一次，一次数据量在20w-30w左右。

1. 入参为一个excel表格文件，传入后解析文件，将数据分为语音反馈和文字反馈，入库存储
2. 如果是文字反馈，直接通过mq发消息给ai分析，储存分析结果
3. 如果是语音反馈，通过mq发消息给asr语音转文字，转文字后再发消息给ai高分析，储存分析结果
4. 通过sql语句查询导出数据，涉及到sql对json数据的解析

- 业务延伸：后续接了一个师训质检的任务，需要分析老师们上课的视频，将大批量mp4格式转为mp3格式后通过excel批量传输，成功将公司业务从文字/语音质检拓展到视频质检

#### ASR接口迁移

- 背景：本系统的ASR分为两种：同步ASR与异步ASR，其中大部分用的是异步ASR，通过mq实现，但是异步ASR仅支持.mp3格式。业务需要将微信语音转文字但微信语音为.silk格式，因此采用另一个同步ASR接口进行转换。但该接口开销太大，需要将微信语音asr迁移到异步接口上。

1. .silk格式转.mp3格式，全网调研没有直接用java实现的方式，唯一的方式是通过一个silk-v3-decoder脚本来实现，和公司管理开发平台的人沟通之后让他们将脚本下到了环境中。
2. 转换后的文件仅存在本地，需要上传到线上，通过阿里云OSS对象存储的方式存储
3. 原有的微信聊天分析逻辑：ASR转换完成 -> 发消息让ai分析，改变逻辑为ASR转换 -> 判断一条微信的所有语音是否ASR完成 -> 是，则发分析消息；否，则搁置该分析，等待兜底的job来完成这个分析任务
4. 开发兜底job，定时执行3中所说的分析任务。
5. 新的代码逻辑中，定时任务和常规逻辑可能同时执行这一条微信的分析任务并且发送ai分析消息、在表中创建数据等操作，因此需要针对此逻辑加一个分布式锁，保证数据唯一性
6. 下载文件 -> 格式转换 -> 上传文件 -> 删除文件 这个方法开销较大，在测试环境中测试时负载较大时脚本会出错，因此对此方法通过RateLimiter进行限流处理
7. 在dev环境测试6的功能时出现大量YGC导致OOM，使镜像频繁重启的问题，排查了jvm、容器本身等问题后，最后定位到OOM是容器的OOM，而非jvm的OOM

加锁问题：兜底逻辑和接口逻辑冲突

1.接口和兜底同时执行，同时发了asr（由我加锁解决）

2.接口和兜底同时执行，同时发了ai分析（有现成的兜底逻辑解决）

## 亮点

### ASR迁移

我认为最大的亮点是主导完成了微信语音 ASR 接口的迁移落地，解决了原有同步接口开销过大的问题。

背景是之前微信语音转文字依赖另一个同步转化的接口，但接口成本高、开销大，每次完成ai分析任务时都要等待微信语音转文字完成后拼接整条消息，非常耗时间，因此业务急需将这个接口迁移到异步 ASR 降低成本 —— 但异步 ASR 只支持.mp3，微信语音是.silk，且全网没有通过 Java 直接转换的方案

调研后发现只能通过 silk-v3-decoder 脚本转换，主动协调平台团队将脚本部署
到线上环境，同时设计了 “下载→转格式→阿里云 OSS 存储→删除本地文件” 的完整链路；

确定这个分析思路之后我发现，原来微信分析是等所有语音转文字拼接完再发msg，修改为异步asr的话就不能使用这个逻辑了，因此我将逻辑修改为“先判断一条微信是否全部asr完成，若完成，发ai分析msg，若未全部完成，则遍历每一条语音，针对没有发送asr信息的语音发送asr信息，然后搁置这一条分析任务。我添加了一个兜底的job逻辑，对所有含微信语音的分析任务进行扫描，如果全部asr完成，就通过兜底任务发送ai分析msg”

切换为异步asr后，为了防止并发，出现两个任务分析同一条语音，发送两次asr的情况，对发送asr这一块的逻辑加了分布式锁。

## 难点

### 定位test环境出现的OOM导致镜像频繁重启问题

当时开发完迁移的功能在test环境上测试，发现镜像频繁重启，日志显示OOM，查看监控后发现YGC会上升到一个很高的值，然后镜像重启。一开始我认为是jvmOOM的问题，于是我试图通过Arthas性能监控工具查询jvm信息，未发现异常；我又希望通过jvm的jmap指令找到重启前的dump文件定位问题具体出在哪，结果发现没有dump文件，于是我去检查jvm启动参数，发现有-XX:+HeapDumpOnOutOfMemoryError，排除了jvmOOM的问题，那就只剩容器OOM了，但令我疑惑的是k8sEvent当中并没有warning信息，和容器管理那边的人咨询后发现确实是容器OOM（test环境的pod只有1G），没有warning是他们那边的bug
